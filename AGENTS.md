# Repository instructions

## Build and checks

- Build on Windows with the installed .NET 8 SDK: `dotnet build src/TiaOpennessMcpServer/TiaOpennessMcpServer.csproj --configuration Release`.
- Keep the application a .NET Framework 4.8, x64 WinForms executable targeting the installed TIA Portal V20 Public API.
- Run the Siemens-free .NET 8 harness with `dotnet run --project tests/TiaOpennessMcpServer.OfflineTests/TiaOpennessMcpServer.OfflineTests.csproj --configuration Release`, not `dotnet test`.
- Dashboard script checks: `node --test tests/dashboard.test.cjs`. Architecture/migration checks: `node --test tests/architecture.test.cjs`.
- No active build, test or runtime dependency may point into `reference/legacy-v1/`. This is an inert snapshot of commit `8ebc151`, including coupled tests and former instructions. Do not run its project or lifecycle helper as a fallback.

## Active architecture and publication boundary

- MCP is the primary product interface. The dashboard is its connection, testing and inspection extension; dashboard layout, forms and workflows must not determine engineering operations or MCP contracts.
- Keep engineering operations and managed contracts (`Operations/`), native Openness calls (`Openness/`), shared execution and connection services (`Services/`), neutral diagnostics (`Diagnostics/`), MCP protocol/endpoints (`Mcp/`), dashboard endpoints and assets (`Dashboard/`) and composition/hosting (`Host/`) separate. Operations and services must not depend on MCP or dashboard types. See `docs/architecture.md` for the implemented structure and verification checklist.
- There is one user-started, long-running executable, one HTTP listener, one shared STA scheduler and a server-wide connection registry. MCP and dashboard have separate endpoint responsibilities within that host. Do not introduce another running server, transport, launcher, supervisor or per-client attachments; ordinary internal service classes are allowed.
- Run every TIA Openness call through `StaTaskScheduler`. Native objects remain on that worker; only managed DTOs cross threads.
- The structural transition is implemented. Active dashboard routes use `/api/dashboard/*` and browser requests use `X-Tia-Dashboard: 1`; assets live in `Dashboard/wwwroot/`. Do not restore `Prototype/`, `/api/prototype/*` or the former combined HTML file as active implementations. Preserve the documented twenty-four-tool MCP contracts while keeping callers, tests and documentation aligned.
- Startup defaults to full access: twelve read tools and twelve modifying tools. Explicit `TIA_MCP_ACCESS=read-only` or helper `-AccessProfile read-only` publishes only reads and rejects writes and compilation in the service. The old prototype switch remains a compatibility spelling and cannot restore V1.
- `/mcp` publishes these twelve read tools: list_tia_processes, get_status, list_devices, get_device, list_blocks, get_block, list_udts, get_udt, list_tag_tables, get_tag_table, get_cross_references and export_tag_table. Each dispatches to the existing guarded service. Full access additionally publishes exactly write_blocks, write_udts, create_tag_table, create_tag, create_user_constant, set_tag_entry_attribute, delete_tag_entry, import_tag_tables, delete_block, delete_udt, delete_tag_table and compile_plc. These share the guarded service and STA. There is no write-probe endpoint, arming session or created-object restriction. Retired V1 names, MCP connection actions and hidden legacy dispatch remain forbidden.
- Keep definitions, schemas, dispatch, tests and documentation aligned with the current publication in `docs/project-rehaul.md`, `docs/write-operations.md` and `docs/compile-delete-export.md`. The twenty-four tools are the implemented inventory, not a permanent ceiling on explicitly agreed native operations. Saving projects and PLC upload/download are permanently outside MCP by the user's boundary. The MCP contract harness must exercise production code without a second implementation or listener; it must not require that code to stay in a particular file.
- Keep one authoritative MCP definition and dispatch implementation within the MCP boundary. `Program.cs` should compose/start the application; protocol and route handling belong in their boundary modules. The current source locations are documented in `docs/architecture.md`, not permanent file-location constraints. Preserve client-neutral documentation and keep authoritative source separate from derived content.
- Start documentation lookup at `docs/README.md`. Completed handoffs and migration/probe instructions under `reference/` are historical evidence, not current instructions, publication holds or future-work authorization. Do not restore their restrictions or rewrite their recorded evidence as current verification.

## Connection and discovery rules

- The user connects and disconnects existing UI processes through the dashboard. Open project in TIA is a dashboard action on a closed project tab only: it starts one visible TIA window for that stored path and attaches it. Do not attach headless instances, reconnect automatically, or introduce an implicit active process. MCP cannot start TIA or open a project.
- Project reads and writes require `processId`, an existing user-enabled attachment and the retained native Project. Capture its internal ticket before queueing; validate runtime identity, path and retained native context before/after reads, at collection boundaries and after failures.
- Context loss discards the result, releases only that attachment and requires explicit reconnection. Never adopt a replacement project. Ordinary object/type/permission failures must not invalidate a still-valid context.
- Detach only with the retained `TiaPortal.Dispose()`; `TiaPortalProcess.Dispose()` closes TIA and is forbidden for detach. A failed Open project may close only the incomplete instance that action started.
- Device lookups use the retained project's ObjectIdentifierProvider directly. `plcObjectId` identifies the CPU DeviceItem whose SoftwareContainer owns PlcSoftware, never the rack, Device or software object.
- Block, UDT and tag-table discovery traverse only their native typed compositions and unit scopes, preserve names/order/identity and readable branches, and return no source or detailed metadata. See `docs/project-rehaul.md` for classification and unnamed unit-container handling.
- Individual block and UDT reads resolve one object directly and read metadata using one native GetAttributes(ReadOnly | ReadWrite) call. Do not re-fetch returned attributes through typed properties. Metadata-only reads must not export. Source export is native, read-only and uses per-request temporary files, exact-content checksums, strict explicit formats and guarded best fallback. See docs/get-block.md and docs/udt-discovery-read.md.
- `get_tag_table` uses one bulk table attribute call and the native Tags/UserConstants/SystemConstants compositions. Entries have their own native identifiers or null; never invent IDs. includeEntries:false skips entry access and returns entries:null. This detail reader has no export/XML/source/checksum path. The separate `export_tag_table` calls native PlcTagTable.Export with WithReadOnly and returns SimaticML text/checksums through owned temporary files. Explicit import_tag_tables accepts supplied XML through the write contract. See docs/tag-table-discovery-read.md and docs/compile-delete-export.md.
- Cross-references resolve one object directly and query its native CrossReferenceService with AllObjects. Preserve Sources/Children/References/Locations and native enum/path fields; add IDs only for underlying engineering objects. No extra type allowlist, inventory rebuild, parsing, compilation or derived graph. See docs/cross-references.md.
- Native identifiers are opaque; paths are navigation aids. Device `includePath:false` skips reconstruction and returns null paths.
- Native nonblank project versions are preserved; blank becomes null. Installed portal version is separate. Do not infer update/patch/build/product codes.
- Native error messages retain their text and tia-openness origin; bridge errors remain distinguishable. Never serialize native proxies.
- Add Siemens-free checks to the existing harness. Simulated tests do not establish native lifecycle or inventory behavior.

## Write operations

- Follow native Openness operations. Keep `write_blocks` and `write_udts` as source generation/import operations; do not invent separate create/update block or UDT APIs, update-only modes or member-patch semantics. A consumer updates by reading source, editing the complete document and writing it back in a supported explicit format with the intended native name and scope. Native generation/import determines replacement and affected objects.
- Source writes accept document contents, never client-controlled server paths. Stage exact UTF-8 text internally; use native external-source generation or SD/SimaticML Override imports. Clean up owned temporary sources/files on success and failure; report incomplete cleanup and affected native objects without inventing identities.
- Existing tags/user constants can be edited or deleted directly by ID. `delete_block`, `delete_udt` and `delete_tag_table` resolve the matching native type by its own ID and call Delete once; retain identity before deletion and do not read the deleted proxy afterward. Native restrictions remain authoritative. System constants remain read-only.
- `compile_plc` is an explicit full-access operation using the selected CPU's PlcSoftware ICompilable.Compile(). Return the current invocation's recursive diagnostics; distinguish complete diagnostic retrieval from successful compilation. Do not claim compiler history or force-rebuild support. Other writes never compile implicitly beyond the processing intrinsic to their native operation.
- No save, PLC upload/download, other online action, automatic retry or source-name substitution is exposed. Saving and upload/download remain outside MCP permanently.
- Native writes may partially modify the project on failure. Preserve errors and partial affected objects; do not claim rollback or complete success.
- The user confirmed that earlier writes worked. This is user-reported native evidence, separate from offline tests and the new MCP integration checks.

## Lifecycle and live TIA safety

- Use the `manage-tia-mcp-server` skill before managing this checkout's server. Use only `tools/tia-mcp-server.ps1`, its exact executable checks and token-protected graceful shutdown. Never kill by image name or delete state to bypass ownership checks.
- Build/test first, then load that successful Release build into the single managed server. Report whether the new executable is actually running and that the user must reconnect attachments.
- Saving, writing, importing, creating, compiling, cloning, closing the user's project and online operations are forbidden during read-only validation.
- If TIA requests external-access approval, pause for the user to approve it.
- Before live validation, confirm attachment disposal only detaches and cannot save/close the user's project. If this guard regresses, live verification is blocked.
- Use `docs/evidence.md` for scoped verification. User-reported block/UDT/connection checks remain distinct from agent-executed native acceptance. Native fixtures verify populated user constants, UDT external/SD/ML round trips, the import matrix, explicit compile/delete/export and expanded cross-references. Populated system constants, special safety/protection/software-unit cases and broader native lifecycle transitions remain outside that evidence. Do not repeat already-passed basic discovery checks without a regression concern.
- Historical records preserve their original observations and evidence limits. They do not describe the current running server, authorize new native operations or require replaying completed tests.
