## Local and transport checks

The Release build checks compatibility with the installed API. The Siemens-free .NET harness exercises production managed contracts, guards and service scheduling. JavaScript tests cover dashboard behavior, architecture boundaries, native-runner fixtures and assertions. The HTTP smoke checks exercise the existing endpoint with passive/disconnected requests; they do not establish native engineering semantics.

Dated build, reload and browser observations remain in [architecture verification](../reference/history/architecture-verification.md), [dashboard verification](../reference/history/dashboard-verification.md) and [write integration verification](../reference/history/write-integration-verification.md). Their test counts, process IDs and attachment state describe the recorded checkpoint only. Current build/check commands are in the [repository README](../README.md).

The [codebase and documentation cleanup checkpoint](../reference/history/cleanup-verification.md) records protocol validation, authenticated lifecycle identity, removal of redundant dashboard routes, the managed reload and its passive HTTP checks. It does not add native project-operation coverage.

The [stage 1 refinement handoff](../reference/history/handoff-2026-09-28-before-stage-2.md#verification) records a successful Release build, 146 offline groups and 183 Node checks, plus four skipped live-server checks. It includes request-parser compatibility, shared native-runner safeguards tested with fake transport, SSE framing/admission/disconnect/coalescing and subscription-controlled monitoring. A Windows PowerShell 5.1 memory-stream smoke also verifies the output SDK under .NET Framework with the existing assembly resolver. That session did not reload the server or call TIA.

The [stage 2 handoff](handoff.md#checks-and-evidence-limits) records successful isolated and normal Release builds with zero warnings/errors, 158 Siemens-free offline groups, eleven dashboard Node checks and fifteen architecture Node checks. Those checks cover the in-process boundary path, bounded run history, HTML SSE framing/reconnect, pending transitions, browser action flow and a DOM observer feedback regression. After explicit user approvals, the normal Release executable was started through the guarded helper and later rebuilt and restarted with the observer fix. Live HTTP checks verified the bundled assets and initial HTML SSE patches; a fresh Chrome tab rendered the dashboard. Tool actions, subsequent stream updates and native TIA behavior were not verified, so existing native evidence is unchanged.

A later result-formatting change in [the current handoff](handoff.md#result-formatting-loaded) passed separate-output and normal Release builds, 159 Siemens-free offline groups, eleven dashboard Node checks and fifteen architecture Node checks. After explicit user approval, it was loaded into the authenticated managed server. A read-only browser call to `list_tia_processes` displayed indented JSON. The new offline check verifies unchanged exact Response text and escaped non-JSON text; the browser call is not a native engineering acceptance result.

## Reports and reruns

Native reports are retained locally under ignored `test-results/` directories because they contain project paths, native identities and complete source/requests/responses. The linked records identify run directories, failures, continuations and evidence limits. Their absence in another checkout is not proof that a run passed or failed.

Active runner instructions are in [native acceptance](native-acceptance.md), [the import matrix](native-import-matrix.md), [lifecycle acceptance](compile-delete-export.md#native-acceptance) and [cross-reference acceptance](native-cross-reference-acceptance.md). A new run needs an authorized disposable target already connected by the user. Existing evidence does not authorize another native write, compile, connection transition or replay. Repeat passed checks when a regression concern or an explicitly selected new scenario justifies it.
